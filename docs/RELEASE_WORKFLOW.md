# 提交与发布流程

目标是让一次改动只做一次必要的本地验收，再执行一轮 CI；固定签名、完整 CI、数据保留和页面返回／重开检查继续保留。本机原始记录放 `.cache/emulator-update/` 或 `dist/verification/`，不提交。

## 准备一次

先检查 Git 工作区、远端版本、GitHub 访问、ADB 和 PowerShell。确定 App 版本、模块版本、预装资源及发布说明后再开始检查，避免构建后又改版本号。模拟器已运行时复用；用户要求冷启动时直接执行 `scripts/start-emulator.sh --cold-boot --yes`，不先做一次普通启动。启动设备可与不依赖设备的准备工作并行。

## 本地检查与设备验收

使用 [模拟器更新流程](EMULATOR_UPDATE.md) 一次完成相关检查、构建、覆盖安装及版本／摘要核对。普通页面改动使用相关 `--test`，不另外先执行一遍完整 Flutter 回归；完整回归由 CI 执行。数据库、模块核心或依赖变化仍按原规则扩大范围，需要排查时也可显式执行本地全量。

发布验收按仓库约定使用 `--force`。不要在更新脚本前手动重跑它包含的静态分析、架构检查与相同测试。测试或文档修正而 APK 输入未变化时，后续复验可复用原构建，但仍须通过当前相关检查；不能省略实际版本和摘要核对。

例如模块商店改动：

```bash
scripts/update-emulator.sh --force --verify-catalog --catalog-offline \
  --test test/module_catalog_test.dart \
  --test test/module_catalog_performance_test.dart
```

验收脚本核对最近成功更新记录、实际 APK 摘要／版本及当前构建输入指纹，然后验证详情关闭／返回／重开、搜索清空、筛选恢复、返回上级设置后再打开。`--offline` 加验缓存和恢复在线；`--cold-start` 只停止并重启 App 进程，不重启模拟器。模块包不安装、不卸载，任务和课程不修改。

更新脚本的 `--verify-catalog` 会自动完成商店验收及 App 进程冷启动，`--catalog-offline` 加验离线与恢复在线。页面验收失败时不记录整轮成功，也不执行 `--commit`；安装已成功但验收未通过时，实际设备可能已经更新，见尝试记录。单独复验仍可执行 `source scripts/dev-env.sh` 后调用 `python3 scripts/module_host/verify_catalog.py --offline --cold-start`。

控件定位兼容 Android 文本框的 `hint`、弹窗背景的同名“关闭”标签和展开项合并标签；滚动遇到边界就停止。每个步骤记录耗时，失败写入未完成报告并退出，不能把仅停留在商店首页当成成功返回。

默认报告写入新的 `.cache/emulator-update/catalog-acceptance/` 子目录。`--output` 可指定新目录，已有报告不会覆盖；`--build-report` 可指定对应的成功更新记录。`--dry-run` 只展示步骤，不连接设备。

其他页面仍须按改动范围走通；不相关页面及未变化模块不因“发布”而反复验收。已有同版本模块仍须核对摘要，再复用，不能只检查版本号。

## 一轮 CI 与发布

本地验收通过后，显式提交本次文件，在同一提交上创建新标签，并原子推送 `main` 与 App 标签；有新模块包时一并推送新模块标签。现有工作流已支持 main 等待同提交标签运行，不能再额外触发手动全量构建。

完整 Flutter 分片、静态检查和三 ABI 构建在 CI 并行；固定签名任务在总关卡通过后执行。等待期间可准备报告和核验已经发布的独立模块，避免所有整理工作都排到发布完成后。

main 的普通推送按**最近一次成功 CI 的源码提交**选择任务，涵盖期间尚未验收或失败提交中的改动：

| 改动范围 | CI |
| --- | --- |
| 文档、普通脚本及 Python 工具测试 | 仓库、文档、架构、Python、目录、打包夹具、工作流和 Node 检查；不安装 Flutter、不构建 APK |
| Dart 测试、独立模块或其索引／发布包 | 上述检查、Flutter 分析与完整测试分片；不构建未变化的 APK |
| 宿主、Android、内置资源、依赖、构建／CI 控制脚本或未知文件 | 完整检查、测试和三 ABI 构建 |
| App 版本标签、PR 或手动工作流 | 完整检查、测试和三 ABI 构建；App 标签再执行签名与发布 |

无法确认成功基线、比较关系不是快进、查询失败、文件列表可能截断，均回到完整检查。重命名同时检查旧路径。GitHub 比较接口只在第一页返回至多 300 个文件，达到上限不能据此跳过任务，见 [GitHub 比较接口](https://docs.github.com/en/rest/commits/commits#compare-two-commits)。现有 main／App 标签同提交去重仍优先执行。

CI 失败先查看失败日志。仅环境偶发问题且源码未改时重跑失败任务；修改源码需要新的提交和候选，不能移动已发布标签或覆盖同版本包。保留失败原因，避免靠反复重跑掩盖不稳定测试。

## 下载核验与记录

公开发布后核对 APK 的源码提交、版本、ABI、固定证书、摘要与内置模块；模块包核对身份、版本和摘要。作者索引分支只在对应模块包已公开且核验通过后快进。

raw 内容可能短暂返回 CDN 中的旧索引。核对分支提交与不可变标签内容后，记录缓存差异并有界重试原公开 URL；不因 CDN 缓存重复发布模块。最后提交精简验收报告，检查 `main` 已推送且工作区干净。

## 2026-11-03 的耗时基线

成功的 beta.20 CI 为 **8 分 30 秒**，其中三 ABI 构建约 7 分 33 秒、测试分片约 6 分 41 秒至 7 分 9 秒，二者并行；签名 23 秒、发布 10 秒。此前临时编写和修正商店驱动占用约 9 分钟；另有一次候选因动画等待断言失败，需要修复并重新发布。相关版本、CI 链接和设备范围见 [验收报告](verification/release-20261103-beta20.json)。

同日固定脚本在现有 beta.20（versionCode 4220）上实测 **128.301 秒**：打开商店 14.401 秒、详情 14.821 秒、搜索 5.849 秒、筛选 9.942 秒、离线与恢复在线 55.073 秒、返回重开 20.296 秒、应用冷启动 7.482 秒。脚本核对了实际 APK 摘要和构建输入指纹；278 项 Python 工具检查通过。本轮只改流程工具与规范，没有重建、安装或重新发布 APK／模块。记录在本机 `dist/verification/releases/workflow-optimization-20261103/`。

此前的 9 分钟包含临时编写和调试驱动，两者统计口径不同，不能据此计算脚本运行速度的加速倍数。

完整发布的下一次实测应分别记录准备、本地检查、设备验收、CI 和下载核验，不能把脚本单次耗时当作整轮发布耗时。

后续合并命令实测 **133.736 秒**，包含静态分析、架构检查、相关 Flutter 回归和完整商店／离线／冷启动验收；复用已核验的 beta.20 APK，跳过重建与重复安装。290 项 Python 工具测试、36 项目录工具测试、22 项 CI 分流／总关卡专项及固定版 actionlint 通过。真实 GitHub 成功基线与提交比较证明，`35d899b` 验证后的 `5f94cae` 文档提交应选择工具检查；App 标签仍选择完整检查。新 CI 在 GitHub runner 上的耗时尚待下一次推送验证，且修改 CI／构建控制脚本的首次提交本身仍须完整检查。本机证据在 `dist/verification/releases/workflow-simplification-20261103/`。
