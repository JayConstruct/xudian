# 冷启动与 UI 规则优化路线

记录日期：2026-10-14。本文保存优化建议、验收目标及首轮推进状态；建议与已完成实现分别记录，不将代码完成等同于真机提速。已实现的加载优化见 [UI 加载性能](../UI_LOADING_PERFORMANCE.md)，当前界面规则见 [界面设计系统](../UI_DESIGN_SYSTEM.md)。

建议先建立冷启动基线，再依据采样优化启动关键路径；同时统一 UI 规则来源，将设计规则落实到主题常量、公共组件和验收场景。

## 优先级

| 优先级 | 优化项 | 具体做法 | 交付与验收 |
| --- | --- | --- | --- |
| P0 | 建立冷启动基线 | 分别测量首帧、首页真实内容就绪、可交互时间；固定设备、数据和模块版本，重复采样 | 基线报告包含样本数、原始结果、中位数与 p95，以及主要耗时阶段 |
| P1 | 减少启动必需工作 | 根据采样评估非首页模块脚本延迟加载，以及启动清理任务后移 | 相同条件下前后对比；首次打开其他模块、依赖及失败恢复不出现回归 |
| P1 | 统一设计规则 | 对齐文档、主题常量和公共组件，解决规则冲突 | 形成冲突清单，确定统一值及允许覆盖的场景，代码与文档同步 |
| P2 | 完善页面状态 | 统一加载、空数据、错误、重试、提交中与成功反馈 | 页面状态和操作结果对应，失败保留可重试内容与草稿 |
| P2 | 建立视觉验收 | 使用组件示例页检查浅深色、窄屏、大字号、键盘与减少动画 | 可重复的场景检查与必要的截图记录，关键交互具有自动化回归 |

## 冷启动：当前依据与候选优化

当前 `client/lib/main.dart` 直接调用 `runApp()`，没有在调用前等待业务初始化。`client/lib/app/app_shell.dart` 已并行读取保存布局与恢复模块宿主，首页工作区仍等待恢复完成。

`client/lib/core/module_host/module_host.dart` 在恢复过程中按依赖顺序逐个激活已启用模块；每个普通脚本模块会加载计算与工作流两个 worker。这是值得采样的候选瓶颈，尚不能断言其占时最多，也不能据此给出提速百分比。

现有 `UiLoadTrace` 已覆盖数据库准备、宿主恢复、包校验、worker 加载、壳层恢复、页面排队与执行等阶段。事件含义和已有优化见 [UI 加载性能](../UI_LOADING_PERFORMANCE.md)；本路线优先补齐平台启动与首页可交互指标，不重复实施已经完成的并行读取、校验去重和日期缓存。

### 测量方法

- 区分已安装应用的进程冷启动、首次安装初始化、温启动与后台恢复；分别记录，不混合统计。
- 区分平台首屏显示时间（TTID）、首页真实内容就绪与可交互时间。若接入 `reportFullyDrawn`，应在定义好的首页可用条件满足时报告完全显示时间（TTFD）。
- 固定设备、构建模式、模块版本和数据集；记录样本数、中位数、p95 与阶段耗时，低数据量和大数据量分别比较。
- 使用模拟器验证测量流程；性能结论以同一 ARM64 真机的 profile/release 对比为依据，profile 用于阶段分析，release 用于最终启动表现复验。
- `app.start` 不包含原生进程与引擎启动；`page.firstFrame` 不等于屏幕呈现时间。嵌套阶段不能直接相加，平台启动时间也不能替代业务内容就绪时间。

Android 指标定义见 [应用启动时间](https://developer.android.com/topic/performance/issues/launch-time?hl=zh-cn)。真机与 profile 模式的使用依据见 [Flutter 性能分析](https://docs.flutter.dev/perf/ui-performance)。

### 根据采样决定的改动

1. 评估先恢复模块描述、依赖和导航，再加载首页实际需要的脚本；其他模块首次使用时准备。
2. 检查启动清理与维护任务能否在首页就绪后执行。只有不影响数据一致性、迁移、包校验和恢复安全的工作才可后移。
3. 保留依赖顺序、脚本初始化副作用、权限语义和失败恢复入口；延迟加载时同时测量首次打开其他模块的耗时。
4. 分步调整，每步使用相同条件复验，避免一次改动过多导致收益来源无法判断。

## UI：统一规则来源并落实到组件

当前存在一个具体冲突：[界面设计系统](../UI_DESIGN_SYSTEM.md) 将内容卡片默认半径写为 16，而 [柔和极简规范](SOFT_MINIMAL_UI.md) 和 `client/lib/core/ui/ui_design.dart` 的 `AppDesign.radius` 使用 20。

首轮已依据公共实现将卡片默认半径统一为 20，并对齐 Chip 形状、日期动效、截图限制等规则；冲突与修正依据见 [UI 规则核对](UI_RULES_AUDIT.md)。本文保留上述问题作为初始发现，不直接改变现有视觉值；宿主默认规则与 UI 包允许自定义的范围应明确区分，组件与 UI 包契约继续遵循 [公共 UI 与界面包](../UI_COMPONENTS.md)。

| 规则类别 | 需要统一的内容 |
| --- | --- |
| 尺寸与层级 | 间距、文字层级、内容宽度、圆角、点击区域，以及窄屏和大字号适配 |
| 页面状态 | 何时保留旧内容、何时显示进度；空数据、错误、重试、提交中与成功反馈；失败后保留草稿 |
| 动效 | 按操作类型定义时长；连续操作、反向操作、取消、减少动画与高对比模式的行为 |
| 模块边界 | 哪些样式可自定义；哪些反馈、审核内容和恢复入口由宿主统一提供 |

规则落地优先使用主题常量与公共组件，减少页面自行定义尺寸、状态和动效。组件示例页应覆盖正常、加载、空数据、错误、禁用和提交中等实际状态，而不只展示静态外观。

视觉验收覆盖浅色、深色、窄屏、宽屏、长文本、大字号、键盘、减少动画与高对比模式；同时检查点击、焦点、读屏语义、滚动和草稿保留。现有真机体验任务及剩余验收范围见 [体验优化与跨平台待办](UX_PLATFORM_BACKLOG.md)。

## 建议的下一轮交付

1. 冷启动基线报告：说明首页可用的判定条件、采样方法、原始结果和主要耗时阶段。
2. UI 规则冲突清单：列出文档与代码差异，确定统一规则及合理例外。
3. 根据采样修复最大的启动瓶颈，提供前后对比和相关回归结果。
4. 用公共组件落实统一后的 UI 规则，并补齐对应的页面状态与视觉验收场景。

基线完成后再设置具体性能目标；在获得真实采样之前不承诺固定启动时长或提速比例。

## 首轮推进状态

用户要求通过子 agent 实施，启动与 UI 两个方向分别修改，由主 agent 整合验收。

| 项目 | 已完成实现 | 后续边界 |
| --- | --- | --- |
| 启动观测 | 增加 Dart 首帧与可用工作区计时；Android 接入 `reportFullyDrawn` 与固定就绪标记；恢复失败／无工作区独立报告 | 可用内容树不保证所有业务或网络请求成功；原生 `Activity.onCreate` 到就绪的耗时不是平台 TTFD |
| 可重复采样 | 新增 `scripts/benchmark_startup.py`，验证进程退出，保留原始计时、p50／p95；可按 PID 与本轮 token 等待就绪，不清数据或 logcat | 旧 APK 没有首页就绪标记，只有启动代理指标可作前后比较；结果与口径见 [冷启动采样与验收](../STARTUP_PERFORMANCE.md) |
| 启动查询 | 合并安装与包来源查询；预装来源回填批处理，保留来源、不跳过包身份及完整性校验 | 查询次数减少是结构性证据；全模块懒启动与维护任务后移仍待阶段采样决定 |
| UI 规则 | 统一公共规则来源，对齐圆角、日期动效和界面包作用范围，补齐间距、文字层级、页面状态与验收矩阵 | 新规则是修改页面时的验收要求，不声明所有既有页面已经满足 |
| 日期交互 | 在已有点击／语义门控处增加同条件焦点排除，等待与淡入期间避免键盘触发业务；显式导航保留 | 进入过渡正常失焦，结束或取消后可重新聚焦，不自动抢回焦点；保留 controller 与草稿，不承诺所有内部 State 跨日期不变 |

阶段回归、模拟器对照和构建安装结果按实际验收更新 [验证记录](../VERIFICATION.md)。ARM64 真机性能、具体页面视觉校准及全局状态覆盖仍是后续任务。

## 第二轮：深层启动优化

继续按实际阶段排查，已实施三项运行时改动：SQLite 初始化与迁移前备份移到数据库 isolate；worker 定时轮询改为原生消息通知；验证包移除多余复制并复用脚本解码与冻结声明。保留模块立即初始化、双 worker 隔离、包验证、备份与事务语义，没有把副作用延后到首次访问。

新增 opt-in 启动阶段采样，默认正式版关闭；采样脚本能分组报告数据库、包校验、worker 与首页面准备，而非仅有平台启动代理指标。本地原生包输入已纳入模拟器构建缓存与回归范围。完整 Flutter 与安全回归、设备前后数据和微基准分别记录在 [启动验收](../STARTUP_PERFORMANCE.md) 与 [验证记录](../VERIFICATION.md)。微基准改善不直接换算为真机冷启动百分比，全模块懒启动及启动维护任务后移仍需结合后续采样决定。
